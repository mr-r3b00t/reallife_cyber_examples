Automated web vulnerability scanner, run on a schedule. It started as small recon passes of about 110–125 requests and changed on 10 Nov into full exploit sweeps of 3,000–6,200 requests in under 7 minutes. Each sweep starts at about 01:06 UTC.

ModSecurity is in DetectionOnly mode, so it logged these attacks and blocked none of them. The 18 Nov sweep used up the server's memory and the kernel killed Apache, MySQL and Defender. The site was down for about 32 hours.

The logs show no sign that an exploit worked. Every 200 response I checked was an ordinary page or a default empty response. This was a log review, not a full forensic examination.

What happened to the requests

Not blocked The ModSecurity rules only log

Both ModSecurity configs set SecRuleEngine DetectionOnly, and the custom WFLX rules use pass. ModSecurity logged 582 webshell hits, 290 code-execution hits and 324 parse-error hits for this IP, and let every request through.

Partly blocked 2,824 requests got a 403

These were mostly XSS, SQL injection, path traversal and WordPress probes. ModSecurity wasn't blocking anything, so the 403s probably came from Wordfence or from Apache access rules such as /server-status.

Overload 71% of responses were HTTP 500

15,211 requests got a server error. The error log shows WordPress losing its database connection ("MySQL server has gone away") during each sweep. So the scanner was taking the site down every night, not just on 18 Nov.

No exploit worked The 415 HTTP 200 responses looked harmless

Spot checks: the PHP-CGI injection got the normal 23 KB homepage back, because PHP runs as an Apache module, not as CGI. The admin-ajax.php plugin actions returned a 0-byte or 5.5 KB default response. The Ignition RCE attempts all returned 500 or 301, and the XML posts to /sitemap.xml got the normal sitemap.

Each 200 is classified by response size and path. The response bodies weren't kept, so this is strong evidence but not proof.

Other services The IP didn't touch SSH or anything else

The IP doesn't appear in the systemd journal, auth.log or the firewall log. All activity was HTTP/HTTPS through Cloudflare.

Recommended actions

  1. Find out whether this scan was authorised. One run labelled itself CAIT; authorized pentest, and every run left CAIT-LOG-… markers. If it's your scanner or a contracted test, lower its rate or point it at a staging copy. If not, treat it as hostile.
  2. Block the IP at Cloudflare, since all of its traffic comes through Cloudflare. Then add a rate-limiting rule, such as challenging any IP that sends more than 300 requests a minute.
  3. Only let Cloudflare reach the origin. Firewall ports 80 and 443 on 138.68.136.96 so they accept connections from Cloudflare's IP ranges only, which stops scanners bypassing the edge.
  4. Move ModSecurity to blocking mode (SecRuleEngine On), with OWASP CRS at paranoia level 1, after a short tuning period. Change the WFLX rules from pass to deny where they're reliable.
  5. Confirm the 30 Oct web-root changes (0000000000test.php and the Shapely theme's index.php), and run wp core verify-checksums and wp plugin verify-checksums --all.
  6. Done 19 Nov: Apache workers capped at 20, 2 GB swap added, and Apache restarts automatically after a failure.
